# 研究与对战规范

## 数据、旧版本对照与阵容设计

1. 以 Riot 官方补丁/热修说明核验变更，抓取与该版本一致的英雄、技能、羁绊、装备数值；同时检查模拟器目录和实际响应中的基础数值是否匹配。保存版本标签、URL、抓取时间与原始快照，不能把旧版数据只改标签。
2. 默认延续 NA / Ranked / Diamond、Master、Grandmaster、Challenger 的筛选，按出场率而非胜率排序，禁止自动扩大地区或段位。固定地区后不要把国服和美服混成一个排名。
3. 每次手动运行时保存当前版本热门榜及完整推荐棋盘，以便下一版使用。上一版本对照选其末次可核验快照，记录统计时间窗和样本数。首次若找不到上一版本历史，不用当前榜冒充；报告缺口并保存当前榜为下一版基线。
4. 冻结旧热门十套的阵容、推荐棋格和装备后，双方均使用新版本数值交战。赛季更替导致旧单位不存在时，明确不可直接跨赛季对战，不编造对应单位。
5. 从数值变更、启动速度、D(t)、前排存活、羁绊与装备适配筛出有依据的新阵容。默认先提出 3 个有差异且可成型的候选；若证据只支持更少，应说明而非凑数。不要只给原 Gromp 阵容换皮，也不要预设它强。
6. 对候选解释关键增益、6/7/8级成型路线、经济与追三难度。主要比较完整成型阵容；默认八人口，确有推荐九人口成型的对照需明确标注，不能暗中削成八人口。

## 固定对战规则（双方一致）

- 每队恰好 9 件普通成装：主坦 3 件、主 C 3 件、副 C 3 件。延续“一套前排、两套后排/输出装”。不额外加神器、光明、转职等。装备选对应当前版本且适合该单位的推荐组合，保存具体名称与 API id。羁绊固有标记不冒充额外成装，逐项记录分配。
- 主 C、主坦的目标星级依据各自费用：1/2费三星；3费做两星和三星两个场景；4/5费两星。副 C 和其他单位默认两星。双方遵循同一规则。
- 若主 C 和主坦都是3费，至少分别做“两者两星”和“两者三星”场景，清楚标注是共同变化；涉及混费时按每名核心各自费用设置。不同星级场景分别统计，不能混成单个胜率。对手有3费追三核心时，也保留两星/三星对照，不能只拿弱星级对手测试。
- 每个候选星级配置与每个对手星级配置各跑 10 场真实单场模拟；因此至少每个候选 100 场，有星级分支时更多。固定输入、独立重新抽样，不把重播或缓存同一响应算新场。
- 有已证实 seed 接口才用固定、可复现的十个种子；接口不支持则保存独立请求、响应、时间戳并披露不可完全复现随机性。不得虚构 seed 字段有效。
- 对手按来源推荐棋格逐格录入。新阵容按射程、第一施法覆盖、AoE 暴露、坦克承伤和保护主 C 设计站位，并固定棋格。不能把所有队套同一个站位模板。
- 强化默认双方无额外强化；历史叠层和可选特性必须显式记录，不能把依赖叠层的对手默认削成零。原研究指定的小法 +80 法强、茂凯 +600 生命仅在同赛季同机制确认适用时沿用；版本或机制已变时查证后列新假设，不盲抄。
- 先小规模校验两边响应：单位、星级、装备、棋格、基础数值、叠层与标记是否真的生效，再跑批量。必要时交换左右阵营做正确性排查。发现单边全胜等异常先审计，不直接宣布最强。
- 尊重 AlphaSim 实际额度与限流，串行或按其许可的低频运行；遇429按 Retry-After暂停，可断点续跑，不绕过限制或购买额度。

## 输出与可靠性

- 每个 matchup 保存原始 request/response `.json.gz`、版本与来源、输入哈希和 trial 编号。生成兼容 `tft-replay-session/v1` 的批次文件供现有分析工具打开，注意每批最多100场和512MB解压限制。
- 中文 HTML + Markdown 报告包括阵容/棋格/星级/9件装备、每组胜/负/平与10场样本量、主副C及全队 D5/D10/D20、出伤延迟、前排/主C存活和主要失败方式。汇总显示中位数、Q1/Q3、有效n/N；可加10场胜率置信区间，不能把模拟胜率当排位胜率。
- D(t) 读取不晚于t的最近原始累计伤害快照。记录不到t时缺测，不能补零或用终局伤害代替；死亡后残留伤害按日志保留。末帧伤害单列。运行时召唤物按 ReplayChamps 对齐，出生前补齐快照不得计入。
- 引擎未更新或无法验证时，明确“候选推测/等待模拟器更新”；旧引擎只能作为单列探索，不能贴新版本结论。没有证据不能生成虚构战斗。
- 每版本最终给出值得试的阵容、相对旧十套的优势/劣势及适用条件；如果没有可靠新发现就如实报告。报告中保留来源直链。
